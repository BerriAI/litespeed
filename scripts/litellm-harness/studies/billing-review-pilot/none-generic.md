## Defect 1 — Full-rate audio/text buckets are never reduced for cached splits (overbilling)

`generic_cost_per_token` reduces `text_tokens/audio_tokens/image_tokens` for cached modalities at lines 1227–1237, but only when the union of nested values is nonzero. More importantly, `_calculate_input_cost` at lines 947 and 966 also charges full-rate `text_tokens` and `audio_tokens` after the reduction. In the supplied task example this is fine **if** reduction runs. But the reduction at 1235–1237 writes into `prompt_tokens_details` after `parse_prompt_tokens_details` has run, and `parse_prompt_tokens_details` capped the nested allocations with `_cached_token_allocations`. For 64 text / 128 audio cached and aggregate 192, the allocations are preserved (64 + 128 = 192), so reduction yields 52 text, 39 audio.

However, when only *some* events supply the nested split and the aggregate cached count is smaller than the requested split, `_cached_token_allocations` caps the split cumulatively. If a later merged response has larger full-rate buckets but the same aggregate, reduction can still leave a residual full-rate charge that the cached buckets already paid for. Minimal input: `text_tokens=116, audio_tokens=167, cached_tokens=1, cached_tokens_details={text:64,audio:128}`. `_cached_token_allocations` returns `{text:1,audio:0}` (lines 800–804), so reduction only removes 1 text token; `_calculate_input_cost` bills 115 full-rate text + 167 full-rate audio + 1 cached text. Expected: cached bucket capped at aggregate (1) should correspond to a single modality allocation, but the *audio* cached request is silently dropped; the task requires capping at aggregate, not silently reordering modality priority. This misattributes cached audio.

Affected lines: 800–804, 1232–1237.

## Defect 2 — Audio cache-read rate not exposed in `get_token_type_cost_breakdown` when audio split is absent from `cache_read` ordering

`get_token_type_cost_breakdown` computes `cached_audio_tokens = min(_cached_audio_token_count(usage), cache_read_tokens)` (line 1574), then bills `(cache_read_tokens - cached_audio_tokens) * rates.cache_read_input_token_cost + cached_audio_tokens * rates.cache_read_input_audio_token_cost` (1587–1588). But `_calculate_input_cost` at line 960 bills `(cache_hit_tokens - cached_audio_tokens) * cache_read_cost` only when `cached_audio_tokens` is truthy; otherwise it bills the entire `cache_hit_tokens` at text cache rate (line 963). When nested audio is 0 but nested text/image are nonzero, the totals path bills all cache_hit at text rate — consistent. The breakdown uses `min(_cached_audio_token_count, cache_read_tokens)` which is 0 in that case, so it too uses text rate. Consistent.

But when `cache_read_input_audio_token_cost` is missing from `model_info`, `_calculate_input_cost` falls back to `cache_read_cost` (958–959), while `get_token_type_cost_breakdown` uses `rates.cache_read_input_audio_token_cost` directly (1588) without a fallback. `get_billed_token_rates` determines that value; if it returns the text rate on absence, they agree; if it returns 0.0 or None-derived, the breakdown diverges from input billing, violating "make the breakdown agree with input billing."

Minimal input: model lacking `cache_read_input_audio_token_cost`, usage with `cached_tokens=100, cached_tokens_details={audio:100}`, audio cache rate absent. Expected cached-audio cost = 100 × `cache_read_input_token_cost`. If `rates.cache_read_input_audio_token_cost` is 0.0, breakdown reports 0 while totals report nonzero. Affected lines: 958–961 vs. 1587–1588.

No requirement is demonstrated that these egregious cases are in scope beyond the stated task; I report them as the two strongest concrete correctness defects visible in the supplied source.
